## What this repo is

A personal dotfiles collection managed with [chezmoi](https://www.chezmoi.io/). This repo *is* the
chezmoi source directory (would be checked out at `~/.local/share/chezmoi`). Files use chezmoi's
naming convention: a leading `dot_` in the source maps to a leading `.` on disk (e.g.
`dot_config/fish/...` → `~/.config/fish/...`, `dot_vimrc` → `~/.vimrc`). There's no per-tool nesting
like a stow layout would have — `dot_config/` is one shared tree holding every XDG-style app config.

- `chezmoi apply` — deploy the source state to `$HOME`.
- `chezmoi diff` — preview what would change before applying.
- `chezmoi add <path>` — pull an existing dotfile from `$HOME` into the source tree (renames it to the
  `dot_`-prefixed form automatically).
- `chezmoi edit <path>` then `chezmoi apply` — edit a managed file and re-deploy it.
- `.chezmoiignore` lists paths chezmoi should never manage — currently generated/runtime app state
  (fish's `fish_variables`, JupyterLab's `lab/workspaces/`) that the apps themselves rewrite and that
  shouldn't be templated or diffed like real config.

The repo currently spans two eras of setup:
- **Active (macOS, chezmoi-managed)**: `dot_config/fish`, `dot_config/kitty`, `dot_config/nvim`,
  `dot_config/ranger`, `dot_config/joshuto`, `dot_config/zathura`, `dot_gitconfig`, `dot_jupyter`,
  `dot_tmux.conf`, `dot_vimrc`, `dot_vimrc.plug`, `dot_doom.d`, `dot_bashrc`, `dot_zshrc`. These are
  what the README and recent commit history focus on.
- **Legacy (Linux i3 rice, not yet migrated)**: `awesomewm/`, `alacritty/`, `compton/`, `dunst/`, `i3/`,
  `i3blocks/`, `nitrogen/`, `optimus-manager/`, `picom/`, `polybar/`, `rofi/`, `xresources/`, `gtk3/`.
  Still in the old per-tool-folder-mirroring-`$HOME` layout from before the chezmoi migration; kept for
  reference and not deployed via chezmoi. Migrate a tool by moving its files under the chezmoi
  `dot_`-prefix convention when it's next touched.

There's no cross-tool code to "build" — changes are edits to individual config files. Verifying a
change means understanding the target application's config format (fish script, Lua, Vimscript,
TOML/INI, etc.), and running `chezmoi diff` / `chezmoi apply` to confirm it deploys as expected — not
running a test suite.

## Neovim config (`dot_config/nvim`)

Lua config using [lazy.nvim](https://github.com/folke/lazy.nvim) as the plugin manager.

- `init.lua` — entry point, requires `core.options` and `core.lazy`.
- `lua/core/` — non-plugin setup: `options.lua` (vim options), `keymaps.lua` (global keymaps),
  `lazy.lua` (bootstraps lazy.nvim and loads everything under `lua/plugins/`).
- `lua/plugins/` — one file per plugin, each returning a lazy.nvim plugin spec table. Adding a plugin
  means adding a new file here (or another entry in an existing spec) rather than editing a central list.
- `lua/helpers/` — small shared utilities imported by plugin specs (e.g. `colorscheme.lua`,
  `keys.lua`, `buffers.lua`).
- `lazy-lock.json` is the plugin version lockfile — don't hand-edit it; it's regenerated by lazy.nvim.

## Fish config (`dot_config/fish`)

- `config.fish` — main entry point (aliases, env vars, abbreviations, sourcing).
- `conf.d/` — files here are auto-sourced by fish on startup (e.g. keybindings, theme, fzf setup).
- `functions/` — one fish function per file, filename must match the function name (fish autoload
  convention). Many `_fzf_*` functions implement custom fzf-driven widgets (history search, git log/status
  search, directory search, etc.) wired together by `fzf_configure_bindings.fish`.
- `completions/` — custom/vendored completion scripts for tools (`bun`, `copilot`, `fisher`, fzf key
  binding helpers).
- `fish_variables` (fish's serialized universal-variable state) is intentionally excluded via
  `.chezmoiignore` — it's regenerated by fish itself, not hand-edited config.
