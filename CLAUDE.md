# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A personal dotfiles collection managed with [GNU stow](https://www.gnu.org/software/stow/). Each
top-level directory is a stow "package" that mirrors `$HOME` from that point down — e.g.
`fish/.config/fish/config.fish` stows to `~/.config/fish/config.fish`, `bash/.bashrc` stows to
`~/.bashrc`. Stow just symlinks; there's no renaming convention, no templating, no separate
source/deploy step — edit a file in the repo and the live symlink picks up the change immediately.

- `stow -t ~ <package>` — symlink a package's files into `$HOME` (run from the repo root).
- `stow -n -v -t ~ <package>` — dry run, shows what would be linked/conflict without touching anything.
- `stow -D -t ~ <package>` — remove a package's symlinks.
- `stow -R -t ~ <package>` — re-stow (unstow + stow); use after adding/removing a file in a package.
- See [STOW.md](STOW.md) for a full situation → command → effect cookbook and [SETUP.md](SETUP.md) for
  bootstrapping a new machine.

The repo currently spans two eras of setup:
- **Active (macOS, stowed)**: `bash`, `zsh`, `git`, `tmux`, `vim`, `fish`, `kitty`, `nvim`, `ranger`,
  `zathura`, `joshuto`, `herdr`, `claude` — each symlinked into `$HOME` via `stow -t ~ <package>`
  (`claude` holds Claude Code skills; create `~/.claude/skills` before stowing it, see STOW.md). These are what
  the README and recent commit history focus on.
- **Windows**: only the `claude` package is used. There's no stow, so each skill folder under
  `claude/.claude/skills/` is linked into `%USERPROFILE%\.claude\skills\` with a directory junction
  (PowerShell snippet in [STOW.md](STOW.md#claude-skills)). Re-run it after adding a new skill.
- **Dormant**: `doom/` (`.doom.d`) and `jupyter/` (`.jupyter`) exist in the repo in the same
  package layout but are **not stowed** — not yet reviewed for deployment. The live `~/.doom.d` and
  `~/.jupyter` are real, independent files untouched by this repo until someone runs `stow -t ~ doom`
  (or `jupyter`) deliberately.
- **Legacy (Linux i3 rice, not deployed on macOS)**: `awesomewm/`, `alacritty/`, `compton/`, `dunst/`,
  `i3/`, `i3blocks/`, `nitrogen/`, `optimus-manager/`, `picom/`, `polybar/`, `rofi/`, `xresources/`,
  `gtk3/`, `nvimbackup/`. Already in the same stow-compatible per-package layout (e.g.
  `alacritty/.config/alacritty/alacritty.yml`), kept for reference and never stowed here.

There's no cross-tool code to "build" — changes are edits to individual config files. Verifying a
change means understanding the target application's config format (fish script, Lua, Vimscript,
TOML/INI, etc.), and running `stow -n -v -t ~ <package>` to confirm it would deploy cleanly — not
running a test suite. Since stow only symlinks, editing a file already stowed takes effect immediately
with no re-deploy step.

## Neovim config (`nvim/.config/nvim`)

Lua config using [lazy.nvim](https://github.com/folke/lazy.nvim) as the plugin manager.

- `init.lua` — entry point, requires `core.options` and `core.lazy`.
- `lua/core/` — non-plugin setup: `options.lua` (vim options), `keymaps.lua` (global keymaps),
  `lazy.lua` (bootstraps lazy.nvim and loads everything under `lua/plugins/`).
- `lua/plugins/` — one file per plugin, each returning a lazy.nvim plugin spec table. Adding a plugin
  means adding a new file here (or another entry in an existing spec) rather than editing a central list.
- `lua/helpers/` — small shared utilities imported by plugin specs (e.g. `colorscheme.lua`,
  `keys.lua`, `buffers.lua`).
- `lazy-lock.json` is the plugin version lockfile — don't hand-edit it; it's regenerated by lazy.nvim.

## Fish config (`fish/.config/fish`)

- `config.fish` — main entry point (aliases, env vars, abbreviations, sourcing).
- `conf.d/` — files here are auto-sourced by fish on startup (e.g. keybindings, theme, fzf setup).
- `functions/` — one fish function per file, filename must match the function name (fish autoload
  convention). Many `_fzf_*` functions implement custom fzf-driven widgets (history search, git log/status
  search, directory search, etc.) wired together by `fzf_configure_bindings.fish`.
- `completions/` — custom/vendored completion scripts for tools (`bun`, `copilot`, `fisher`, fzf key
  binding helpers).
- `fish_variables` (fish's serialized universal-variable state) is not tracked in this repo at all — it's
  regenerated by fish itself, not hand-edited config, so there's nothing to add/manage here.
